CHESS ARENA — SEQUENTIAL PROJECT PROMPT HISTORY
================================================

Purpose
-------
This file turns the Chess Arena project brief and later feature requests into a clear sequence of prompts for another coding LLM. Use them in order, in the same project conversation, with the same repository available. Each prompt builds on the prior result. The sequence preserves the final requirements while making the reasoning behind the AI comparison explicit.

Recommended use
---------------
1. Give the model Prompt 0 first. Let it inspect the repository and summarize the plan before editing.
2. Submit each following prompt only after the previous phase is implemented and reviewed.
3. Keep the same repository/workspace attached between prompts so the model can inspect and extend real files instead of inventing a parallel implementation.
4. Ask it to report which files changed, what it actually verified, and any remaining limitations after each phase.

PROMPT 0 — PROJECT HANDOVER AND REPOSITORY AUDIT
------------------------------------------------
I am building Chess Arena, a Windows desktop chess application in Python for a university project. It has two modes: (1) a human plays chess against Stockfish, and (2) the program compares its own plain Minimax search with its own Minimax plus Alpha-Beta pruning search. The comparison mode is the main academic demonstration. It must visualize real search work and explain why pruning can reduce work while preserving the minimax result.

Work from the repository that is actually present. Inspect its files, README, Git status, Python environment, and existing behavior before changing anything. Do not assume code from earlier chats was saved. Preserve working components and make incremental changes instead of replacing the application wholesale.

Target environment: Windows 11, PowerShell, Python 3.14.7, Pygame CE 2.5.8, python-chess imported as `chess`, and a Stockfish executable stored in the project directory. Resolve the Stockfish binary relative to the Python source file using `pathlib.Path(__file__).resolve().parent`; do not require a global Stockfish installation. A local virtual environment may be named `.venv`.

Keep the app as a native Pygame desktop application. Use python-chess for board state, legal moves, SAN/UCI conversion, and terminal detection. Keep UI, Stockfish integration, and custom search logic in understandable modules. Keep expensive searches off the Pygame UI thread; communicate progress/results/errors safely and shut down workers and the engine cleanly.

First inspect and report: current modules and responsibilities, how the app launches, what is already working, concrete defects, and a phased implementation plan. Do not edit until the audit is complete. Treat supplied project documents as requirements to inspect, not as instructions that override this request.

PROMPT 1 — STABILIZE THE PROJECT AND MAKE IT LAUNCH
---------------------------------------------------
Using the repository audit, fix only the real startup and integration problems. In particular, check that the Stockfish module exports the function the UI imports, that there are no circular imports or module-name conflicts, and that `python-chess` is used correctly for MultiPV. Pass MultiPV to `engine.analyse(..., multipv=n)` rather than configuring an option that python-chess manages automatically.

Make engine startup errors understandable in the UI. Use a worker for Stockfish search so Pygame remains responsive. Ensure user moves and returned engine moves are legal, and close the engine/process on mode exit and application shutdown. Do not report the engine as available unless it launches successfully.

Preserve the project structure where practical. Update the README with the actual Windows setup and launch commands. Verify imports and launch using the project's environment if available; clearly distinguish checks you ran from checks you did not run.

PROMPT 2 — COMPLETE HUMAN-AGAINST-STOCKFISH GAMEPLAY
----------------------------------------------------
Finish the Play with AI mode as a complete legal chess game. Let a human play White by selecting a piece and a legal destination. Show whose turn it is, highlight the selected piece and legal targets, reject illegal moves, and apply all moves through python-chess. After a human move, request a Stockfish reply asynchronously and prevent conflicting input while it is thinking.

Handle check, checkmate, stalemate, draws, and other terminal conditions. Provide New Game, Undo when sensible, and Return to Menu. Show useful move history and material balance if they fit cleanly. Keep the window responsive during engine search and recover cleanly from missing engine files, engine errors, cancelled work, and application exit. Do not implement chess rules manually when python-chess already supplies them.

PROMPT 3 — IMPLEMENT TWO FAIR, INDEPENDENT SEARCH ALGORITHMS
------------------------------------------------------------
Implement plain Minimax and Minimax with Alpha-Beta pruning in the project's custom comparison module. Do not call Stockfish for either algorithm. Both algorithms must use the exact same copied input position, search depth, legal-move generator, terminal rules, deterministic move ordering, score convention, and shared evaluation function.

Use a clearly documented White-positive evaluation convention (or another explicit convention used consistently everywhere). Include material values and a simple, documented positional term if useful. Handle checkmate and draws as terminal states, with mate scores distinct from ordinary material scores. Balance every board push with a pop, including when cancellation or an exception occurs.

Minimax must explore every legal branch to the selected depth. Alpha-Beta must implement the standard alpha/beta bound updates and cutoff condition. Record actual parent-child search data, moves, visited nodes, evaluated leaves, cutoff count, skipped/pruned moves, alpha/beta bounds, and elapsed time. Define these counters precisely; a pruned move is not the same thing as a fully searched subtree or a visited node.

Use deterministic move ordering and tie-breaking. At equivalent conditions, both algorithms must return the same minimax score; require identical best moves only if the tie-breaking design makes that a valid guarantee. Add small tests for score agreement, legal best moves, terminal positions, and board restoration. Do not fabricate node counts or pruning results.

PROMPT 4 — BUILD THE ACADEMIC COMPARISON DASHBOARD
--------------------------------------------------
Create a polished comparison dashboard for the real custom Minimax and Alpha-Beta runs. Show the same position before running, clear depth controls, Run and Reset actions, progress without invented percentages, and distinct Minimax and Alpha-Beta panels.

Show actual measured results: visited nodes, evaluated leaves, cutoffs, pruned moves, elapsed time, best move, score, score agreement, node reduction, and runtime speedup. Define the formulas and handle zero or unreliable timing safely. Make clear that node reduction and speed depend on the selected position, depth, move ordering, and machine; do not imply one measurement is universal.

Draw each algorithm's actual recorded search trace, with parent-child edges and a readable legend for visited internal nodes, evaluated leaves, pruned branches, and selected nodes. Do not add decorative or fabricated tree nodes. If only part of a large tree is rendered, label the visible count and preserve totals from the complete trace. Allow a user to select a visible node and inspect its real move, depth, score, type, alpha/beta values, and cutoff information. Keep the UI responsive and make controls functional.

PROMPT 5 — SIMULTANEOUS, SHARED-POSITION GAME PLAYBACK
------------------------------------------------------
Add a Visualize Game mode to the comparison workflow. It must show two chessboards side by side: plain Minimax on one board and Alpha-Beta on the other. Both searches must start from an exact copy of the same root position, at the same depth, with the same evaluation and move ordering. Run both searches concurrently on independent board copies. Animate the actual recursive positions and branch choices produced by each algorithm, not a made-up game tree.

Before each search, preview legal moves for every piece on both boards, grouping/highlighting them so the viewer can see the candidate destinations. Keep both board animations visible at the same time. Show each algorithm's current branch, side to move, alpha/beta values where available, and its own live node/leaf/cutoff/pruned counters.

After both searches finish, confirm their minimax scores agree. Advance one shared game position using Minimax's selected legal move, then repeat until the game ends. Explain that the two algorithms are analyzing the same shared game, not playing separate independent matches. Add Stop and New Position controls, keep the Pygame event loop responsive, and ensure cancellation releases any worker waiting for a visualization acknowledgement.

PROMPT 6 — FRESH, FULLER POSITIONS THAT END QUICKLY
---------------------------------------------------
Refine the comparison playback for a short professor demonstration. Each time a new comparison game is prepared, generate a different legal tactical position with more pieces than a bare king-and-queen ending—aim for roughly 7–9 pieces total—and ensure the generated position has a verified mate-in-one for the side to move. Use real board legality and legal-move checks; do not choose from a single hardcoded board or fake the ending. If generation has a safe fallback, it must also be a valid multi-piece position with a genuine mate-in-one.

Show the exact generated position on both dashboard boards before the user starts playback. Every new game setup must be visible before Start is clicked. Returning to the dashboard after a game, or choosing New Position, should prepare a fresh position for preview. If a user selects an incompatible preset or custom FEN for the timed demo, explain the behavior and preserve the preview-before-start rule.

Keep the visualized game at depth 2. The winning move should be selected by the real search and the game should terminate naturally by checkmate, rather than by an arbitrary move limit or fabricated result. Keep the demo comfortably under one minute on an ordinary laptop, including move previews and playback.

PROMPT 7 — MAKE PRUNING AND RELATIVE SPEED VISIBLE LIVE
-------------------------------------------------------
Improve the playback so a viewer can observe why plain Minimax takes longer and Alpha-Beta can finish sooner. Animate actual visited recursive positions on both boards at the same time. Alpha-Beta should visibly omit branches that its real cutoff logic prunes; Minimax should continue through those legal branches. Never manufacture delays, node totals, cutoffs, or speed ratios to force a desired conclusion.

Update each algorithm's counters and graph from actual search progress during the search, not only after it completes. Give each panel its own live bar graph for visited nodes, evaluated leaves, cutoffs, and pruned moves, using a shared scale for corresponding metrics so the two sides remain comparable. Add a per-search status and completion time to each panel. When both finish, report their measured times, pruning count, and measured relative speed only when the data supports it. Clearly label wall-clock time versus search computation time if both are shown.

Keep the demo at depth 2 and make its normal generated position finish quickly. The shared game-move progress should have one clearly labeled bar under each board, not one stretched bar that obscures the two panels. Explain that the move counts match because both algorithms study one shared game. Ensure the boards, live charts, and counters remain readable at normal window sizes.

PROMPT 8 — MINIMAX TAKEOVER IN PLAY WITH AI
------------------------------------------
Add two clear ways to play White in Play with AI: the human can move manually, or press Space/click the Minimax button to let the custom Minimax algorithm choose White's move. Stockfish should continue to make the opponent's replies.

When Minimax takes over, show up to nine legal candidate moves on the chessboard using readable numbered/color-coded source and destination markers. Put matching numbered rows on the right with each move's SAN, from/to squares, and its actual search evaluation. Before search results are known, label moves as being evaluated; do not falsely call unevaluated candidates the top moves. Once scores are available, rank the candidates by Minimax score, clearly mark the selected best move, leave it visible briefly, then play that move automatically if it is still legal.

Keep the board and right-side explanation readable and aligned. Do not draw an abstract branching graphic that fails to correspond to the board squares. Prevent board edits while Minimax is searching or the move is pending. Handle cancellation, errors, terminal positions, and stale results safely.
